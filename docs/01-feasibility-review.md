# 01 · 可行性审核

审核对象：一份"多 Agent 协作开发架构"设计（50+ 并发 agent、仓库单源真值、两级集成、契约层、风险分档、人签、补丁债棘轮、研究臂、治理层）。

**总体判定：方向成立，可以落地。但有 12 处必须修正、3 处应当否决、8 类风险被遗漏。** 保留的部分占多数，说明这份设计不是空话；需要改的地方集中在"能不能真的并发起来"和"人会不会成为瓶颈"。

## 1. 成立，原样保留

| 主张 | 判定 |
| --- | --- |
| 这是协调成本问题，不是智能问题 | 对。预算投租约/合并队列/契约测试/债务指标，比投"能力评测"回报高一个数量级 |
| 没写进仓库的视为不存在；禁止用对话交接 | 对，而且可机械检查：交接物必须能落成 commit + 记录 |
| 权限绑风险半径，不绑"谁在申请" | 对。挂了 agent 身份作为授权依据的系统都会腐烂 |
| 可验证性决定行为；重构能力 = 特征测试 + 小模块 | 对。这是把"agent 爱打补丁"从道德问题变成工程问题的关键 |
| 独立性只能来自证据面差异 | 对：同权重、同提示的评审，相关性高到没有信息价值 |
| 风险按可逆性分 T0/T1/T2，T2 必须人签 | 对，但必须机械化（见 §2.4） |
| 两级集成 + 分片 CI | 对，这是吞吐主杠杆，不是优化项 |
| 补丁债棘轮 / 特征测试闸门 / churn 触发设计评审 / 重构提案竞争 | 对，性价比排序也基本正确 |
| 尝试预算、租约回收、kill switch、失败即升级 | 对，且实现成本极低，P0 就该有 |
| 不做能力评测授权、不做自由对话式共享记忆、不在主干直提、实现方不产验收判据 | 对，全部保留 |

## 2. 必须修正（12 处）

**2.1 吞吐公式算错。** 原文 `吞吐 ≈ 槽位/时长 × (1−失败率)`，10 槽位 / 15 分钟 / 30% 失败 = 28 次/小时。问题：公式里没有主干。主干合并验证是逐条串行的，评审是有限供给，人签是有限供给。正确的是取最小值：

```
有效吞吐 = min( CI 槽位 ÷ 平均验证时长,
                批大小 ÷ 主干合并验证时长,
                评审容量（评审者数 ÷ 单次评审时长）,
                人签容量（人类可用分钟 ÷ 单次签字时长） )
```

配套两条：主干合并必须**批次化**（一次验证 N 条，否则第一项白算）；容量规划用 Little's law `WIP = 吞吐 × 周期时间` 定 WIP 上限，不要拿 a/f 硬凑数字。

**2.2 租约不能写进仓库锁文件。** 仓库文件做锁 = 单一写热点 + 并发即合并冲突 + 没有原子 CAS，三条里任意一条都足以让 50 并发失效。改为 SQLite（WAL）+ `BEGIN IMMEDIATE` 事务做 CAS，仓库只保留 `lease snapshot` 导出的审计副本。

**2.3 方案缺控制面。** 原文列了治理目标（预算、回收、吊销）却没有调度组件。必须引入单进程 Orchestrator：任务队列、WIP/预算准入、租约管理、事件日志、令牌签发。否则 50 个 agent 各自轮询 git/forge = 惊群 + 配额打爆 + 无法公平调度。

**2.4 相位顺序错。** P0 声称"50 并发不互踩"，但租约排在 P1；凭证签发排在 P4，意味着 P0–P3 期间 agent 手上可能已经有发布凭据。修正：租约进 P0；**从 P0 起 agent 就没有不可逆权限**（缺权限不是问题，多余的权限才是）。

**2.5 路径级租约与重构任务冲突。** 重构要整模块写权。改为三级：`read`（共享）/ `write`（文件或目录）/ `module`（整模块独占）/ `repo`（全仓独占，需人签）。按规范化路径字典序加锁，避免死锁。

**2.6 指纹去重不能硬阻塞。** 硬阻塞会导致同一故障无人认领、误杀竞争提案。改为结构化键 `(路径集 × 失败签名)` 强判重 + 语义相似度仅作 advisory 交协调者裁决。

**2.7 补丁债棘轮不能按 commit 单调。** 加功能必然加行数。改为"模块预算上限 + 赚取额度 + 比率指标看窗口趋势"；per-commit 只守硬上限与"不许升档"。本骨架 `debt-budget` 实现的是硬上限形态。

**2.8 "无锁行为测试"不可直接测量。** 代理指标：公共 API 覆盖率 + golden/snapshot + 变更模块的**抽样** mutation score（全量 mutation 太贵）。

**2.9 "异质评审"要可执行。** 异质 = 不同模型血统 **且** 输入面隔离（只给 diff + 契约 + 失败证据，不给作者推理链）。再加两条防橡皮章：反对率监控（长时间接近 0 = 评审是假的）、对通过抽样复核。

**2.10 人签吞吐是硬约束，靠"收窄签字面"解决不了。** 50 agent 的 T2 会淹掉一个人。正确方向是让 T2 从构造上稀少：不可逆动作收敛为少数流水线命令，配**审批令牌**（HMAC 签名、绑定 diff 摘要、一次性 nonce、带过期）。并且签字必须附可证伪预测 + 回滚方案，事后自动核对——否则签字没有信息量，只是安慰剂。

**2.11 预算缺准入控制。** 只记账不拦截 = 账单后置。必须前置扣减：额度不足直接拒绝 `claim`。本骨架的 WIP 上限就是最小可用的准入控制。

**2.12 模块域 / 租约域 / CI 分片域必须是同一套划分。** 原文 §13 的三个待决项实际收敛成一件事：一张 domain 表（`config/orchestra.toml` 的 `[domains.*]`）。三套边界打架是后期最贵的返工。

## 3. 应当否决（3 处）

1. **用 agent 血统或"能力评分"做授权**——血统统计只能用于路由，用于授权必然过拟合。
2. **逐条合并（无批次）**——主干吞吐不可能达到原文 §7 的数字。
3. **仓库内锁文件做写租约**——见 2.2，直接不可行。

## 4. 被遗漏的风险（8 类）

1. **提示注入**：测试输出、issue 文本、PR 评论是数据，不是指令。runner 需要默认无网 + egress 白名单 + 工具白名单。
2. **供应链**：agent 会加依赖。依赖允许清单 + 锁文件变更列为 T1。
3. **密钥最小化**：agent 环境不得出现部署/云凭据（否则 §2.4 形同虚设）。
4. **可观测性**：原文有指标、没有采集点。需要结构化事件 + `status --json` 快照。
5. **长尾饥饿**：独占租约 + 超长任务会饿死研究臂，需要优先级与抢占规则。
6. **供应商漂移/宕机**：异质性依赖多模型，需要路由降级，且降级不得绕过风险分档。
7. **溯源**：commit 必须带 `Task-Id` / `Agent-Id` trailer 并签名，否则无法回答"这行谁改的、为哪个 intent"。
8. **单机边界**：SQLite 是单机假设（多容器同主机 OK），多主机需 Postgres；接口要留在租约层，不是撒在全局。

## 5. 审核后的结论

保留骨架，替换三处地基（锁 → 事务租约、无控制面 → 单进程控制面、签字 → 令牌），重排相位（租约进 P0、不可逆权限前置）。剩下的问题都是工程量，不是可行性问题。
