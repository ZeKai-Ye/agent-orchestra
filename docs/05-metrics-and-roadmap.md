# 05 · 指标、容量模型与实施路线

## 1. 指标字典（全部来自 `events` 表，不另建埋点）

| 指标 | 定义 | 采集点 | 为什么重要 |
| --- | --- | --- | --- |
| WIP | `claimed + in_progress + review` 任务数 | `status` | 唯一能立刻调的小杠杆 |
| 队列等待 | `claim - created` 的 p50/p95 | 账簿 history | 隐形的成本中心 |
| 合并吞吐 | `gate.passed(stage=merge)` / 小时 | 事件 | 主指标 |
| 回滚率 | revert 数 ÷ 合并数 | 事件（`merge.rolled_back`） | 高合并率下最领先的质量信号 |
| 缺陷逃逸率 | 合并后 7 天内被发现的问题数 ÷ 合并数 | 外部跟踪系统 | 门禁是否在真的筛 |
| 评审反对率 | 有实质反对意见的评审 ÷ 总评审 | 评审记录 | **长期接近 0 = 评审是假的** |
| 人签延迟 | `issue - request` 的中位值与积压长度 | 事件 | 人类是硬约束，必须可见 |
| 可追溯占比 | 有已签 intent 的合并 ÷ 总合并 | 账簿 | 防止需求漂移 |
| 每合并单元成本 | token/分钟成本 ÷ 合并数 | 预算表 | 扩容前必须知道单价 |
| 租约过期率 | `lease.expired` ÷ `lease.acquired` | 事件 | agent 健康与 TTL 是否合理 |
| 重构占比 | `role=refactor` 的合并 ÷ 总合并 | 账簿 | 是否只会打补丁 |
| 补丁债趋势 | 模块行数/复杂度/重复率的窗口斜率 | 门禁 | 长期熵增 |

只看两个数就能判断系统是否健康：**回滚率**（在升 = 门禁在放水）和**评审反对率**（趋零 = 评审是橡皮章）。

## 2. 容量模型（替换原方案 §7 的错公式）

```text
有效吞吐 = min( CI 槽位 ÷ 平均验证分钟,
                合并批大小 ÷ 主干合并验证分钟,
                评审者数 ÷ 单次评审分钟,
                人类可用分钟 ÷ 单次签字分钟 )
WIP 上限 ≈ 有效吞吐 × 目标周期时间（Little's law），再 ×2 留缓冲
```

例：10 槽位、15 分钟验证 → 40/h；批大小 4、主干验证 10 分钟 → 24/h；3 个评审者、每次 12 分钟 → 15/h；人签 30 分钟/天、每次 5 分钟 → 6/h。**瓶颈是人签，不是 CI**。此时正确动作是减少 T2 数量（把不可逆动作收敛成 4 条流水线命令），而不是加 CI 槽位。

按规模换瓶颈：

- 8–15 agent：瓶颈是合并队列与评审质量。
- 20–50 agent：瓶颈是契约漂移与重复工作（指纹去重、契约测试在这里赚钱）。
- 50+：瓶颈是成本治理与目标漂移（预算准入、intent 追溯在这里赚钱）。

## 3. 实施路线（每一步都有可跑的验收）

| 里程碑 | 内容 | 机械验收 |
| --- | --- | --- |
| **M0 方案**（本仓库已完成） | 审核 + 架构 + 数据模型 + 门禁 + 指标 | `verify.ps1` 全绿；文档与代码一致 |
| **M1 协调内核**（已完成） | 账簿、状态机、租约、scope guard、机械门、审批令牌 | 37 用例通过；8 进程抢租约恰好 1 胜 |
| **M2 调度与准入** | WIP 上限已实现；补预算前置扣减、优先级、长任务抢占 | 超预算 `claim` 必须被拒；饥饿用例通过 |
| **M3 分片 CI + 两级集成** | `affected` 计算、模块集成分支、批次合并队列、speculative merge | 单次合并验证时长与失败率进指标；冲突数随批大小下降 |
| **M4 契约层** | `contracts/<domain>/vN/`、消费者登记、生产者提交换全部消费者测试 | 契约漂移类集成错误显著下降（对比基线） |
| **M5 异质评审** | 评审输入面隔离、反对率监控、抽样复核 | 反对率落在 10%–40%；抽检发现率 > 0 |
| **M6 债务棘轮 + 特征测试闸门** | 比率指标、赚取额度、mutation 抽样、重构提案竞争 | 债务趋势下行；无特征测试模块拿不到重构任务 |
| **M7 研究臂 + 反向闸门** | RFC 流程、隔离命名空间、自动回滚、血统冻结 | 自动回滚可在 10 分钟内完成；冻结可由指标触发 |

顺序理由：M1 必须先有（否则并发就是互踩）；M3/M4 是吞吐与漂移的主战场；M5–M7 只有在有数据之后才有意义——没有回滚率数据就调不动评审强度。

## 4. 仍需人类拍板的三件事（已给推荐默认值）

1. **domain 划分**：推荐"现有目录 = 模块 = CI 分片 = 租约域"，先切 5–8 个，超出再拆。写进 `[domains.*]`。
2. **预算配额**：研究臂 10%；单 intent 成本封套；WIP 上限 = 2 × 并行槽位。
3. **不可逆动作清单**：推荐收敛为 4 条（发布、生产配置、数据删除、外部通信），只由人工触发，agent 只能申请。

## 5. 什么时候该停下来重构这套系统本身

三条自检：① 租约冲突率长期 < 1% 且 WIP 从不打满 → 并发规模还没到，别加机制；② 回滚率连续两周下降但缺陷逃逸上升 → 门禁在练"通过率"，需要加异质评审与抽样复核；③ 指标看板没人看 → 先删指标，再加功能。机制的成本是维护机制的人。
